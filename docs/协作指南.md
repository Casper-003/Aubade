## 已确认的工作方式

产品设计按模块逐块讨论，每轮只处理一个小问题或流程。用户明确确认后，立即把当前方案记录下来；提出设想、要求记录或征求意见不等于已经定稿。设计确认、代码实现和使用验收分别记录。

模块编号、范围和当前状态见 [模块划分](模块划分.md)。任务卡引用相应的 M01–M08 编号，方便说明这次在处理哪一块；无需一次展开全部模块。

团队目前有项目发起者和一位积极但没有开发经验的协作者。下面的分工、任务尺度与同步节奏是建议，可按双方兴趣和实际可用时间调整。

## 建议的分工

项目发起者暂时负责产品方向的最终确认、核心开发和合并整合；协作者从一个范围明确的小功能获得完整的交付责任，并参与方案评审。不要只安排整理杂务，也不要求协作者在没有明确规则时独立设计整个子系统。

| 阶段 | 适合交给协作者的工作 | 可交付成果 |
| --- | --- | --- |
| 现在，无需应用代码 | 观察少量参考界面的一个交互 | 3–5 张带说明的截图，分别写清操作、优点、问题及可借鉴之处 |
| 现在，无需应用代码 | 为一个已指定流程画低保真方案 | 正常、空内容、失败等少量状态草图；未决问题单列 |
| 现在，无需应用代码 | 编写曲目样例与边界场景 | 10–15 条虚拟曲目，覆盖同名不同歌手、不同版本、无封面、超长标题等；无需上传歌曲文件 |
| 现在或原型阶段 | 检查文案与任务流程 | 一份明确问题、复现路径及建议的清单 |
| 有可运行版本后 | 按确认方案做体验验收 | 环境、版本/提交、操作步骤、预期与实际结果，以及截图或录屏 |
| 完成基本学习后 | 实现已确认的小型独立界面 | 一个歌曲信息卡、空列表状态等小组件，以及展示截图与 PR |

音频引擎、多人队列规则、整体架构等先由项目发起者组织，协作者可参与验证和讨论；随着能力增长再扩大开发责任。

## 任务颗粒度

一个任务对应一个可展示、可检查的结果。起步可按预计 1–3 小时能够交付的范围试行，学习时间另计，不把估时当硬性考核；若任务需要做多种决定，或持续做却无法展示中间成果，就继续拆分。

- 过大：设计整个点歌系统。
- 合适：为“重复点歌提示”画两种方案，说明提示信息、两个按钮的文案和确认后的结果。
- 过大：开发完整曲库页。
- 合适：按确认的稿件制作一张歌曲卡片，展示正常与无封面两个状态。
- 过碎：修改一处圆角并单独组织一次完整交接。
- 合适：在同一个组件任务中一并检查圆角、间距、文字溢出和按钮状态。

每人同时保留一个主要进行中任务。卡住约 20–30 分钟可以带着已经尝试的内容求助；若是在等待设计确认或缺少材料，及时标明等待什么，不用独自猜测。

## 任务卡模板

每张卡可作为一条 GitHub Issue。当前产品还没有可运行工程时，任务的验收依据应是说明、草图或样例，而不是尚不存在的软件。

```text
标题：一个明确的交付结果
负责人：
对应模块与设计说明：
目标：这次要解决哪个使用问题
本次范围：
暂不包含：
输入材料：已确认规则、参考图或样例
交付物：文件、草图、截图或 PR
验收标准：2–4 条能实际检查的结果
当前状态：待做 / 进行中 / 等待输入 / 待验收 / 完成
下一次反馈节点：例如第一张草图完成时
```

例如“重复点歌提示的低保真方案”：仅讨论同一首歌曲已在待播队列的情况；交付两张方案图及简短说明；验收时检查是否说明谁已点歌、是否能取消、确认后是否明确再加一首。方案是否采用由后续模块讨论决定，画出草图不代表需求已确认。

## 讨论、决定与进度放在哪里

| 位置 | 保存什么 |
| --- | --- |
| 日常聊天或语音 | 快速沟通、澄清、提出问题 |
| GitHub Issue | 一个任务的目标、负责人、当前状态、进展与等待事项 |
| 模块设计说明 | 当前已确认的行为、未决问题、决定理由与验收标准 |
| Pull Request（PR） | 文档/代码的具体改动、验证证据和审阅意见 |
| Vesper_项目记忆.md | 简短全局共识、当前状态与接续位置；不追加完整讨论或操作教程 |

口头或聊天讨论得到结论后，把结论链接回对应任务与设计说明，避免成员必须翻聊天全文才能开工。前期用 Issues 和简单状态即可，不必立刻搭建复杂项目管理体系。

建议每次实际工作结束时，在对应任务下留下四行进展；没有工作的日子无需报空进度。有重要分歧或等待确认时及时沟通，不必等到收工。

```text
本次交付：附文件、截图或 PR 链接
已检查：实际检查过哪些场景
当前卡点：需要谁提供什么信息或做什么决定
下一步：下一次准备完成哪个具体结果
```

避免只说“做了 80%”。例如“已画完正常状态与重复提示，差无封面状态；需要确认预览按钮是否始终可见”更容易接手和反馈。

Casper 的工作方式于 2026-10-29 更新：日常开发、修复、界面调整与文档维护默认在已同步的 `main` 上进行；添加新功能时，再从最新 `main` 新建功能分支。已经合入主分支的旧任务分支不再作为日常开发位置。其他协作者继续遵循上面的个人任务分支约定。项目发起者负责审阅与合并，协作者也可以从使用体验角度审阅，main 保留可接续的状态。仓库内的工作约定不代表 GitHub 服务端已配置分支保护或强制审查规则。

双方尽量分开修改不同文件。共同设计一个模块时，先约定由谁整理结论；另一人通过 Issue/PR 提意见，减少同时改写同一段文字。

参考：[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)、[创建与分配 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)。

### 已经发生冲突时如何处理

先用 `git status` 确认当前是在 merge、rebase 还是 cherry-pick 中，使用 `git diff --name-only --diff-filter=U` 列出尚未解决的文件。已经进入冲突状态时，先解决当前操作，不另起一次合并。

1. 打开冲突文件，逐段对照双方的改动。文本冲突通常以 `<<<<<<<`、`=======`、`>>>>>>>` 标记两边内容；最终结果可以保留一边，也可以将双方需求整合成新的表述或实现。依据当前已确认设计判断，不能只凭谁先提交或整份接受一方来处理。
2. 编辑成最终需要的内容并删除冲突标记。例如一边添加“队列支持拖动排序”，另一边添加“队列支持移除和撤销”，两者可整合为“队列支持拖动排序，并提供移除和撤销”。产品取舍无法从已确认需求确定时，先向用户核实。
3. 检查完整差异，运行 `git diff --check` 并按改动做必要验证；文档检查链接、状态和表述，应用代码按任务运行相应检查。二进制草图等无法逐行合并的文件，需要核对两个版本的内容后选择或重新编辑。
4. 用 `git add -- <已解决的文件>` 逐个暂存处理好的文件。确认没有未合并项后，merge 使用 `git commit` 完成；rebase 使用 `git rebase --continue`；cherry-pick 使用 `git cherry-pick --continue`，后两者若再次出现冲突则重复处理。
5. 推送到本人的任务分支，已有 PR 会显示更新后的内容，再按正常流程合并到 `main`。本流程通过合并最新主分支来同步已共享的任务分支，不使用强制推送覆盖共享历史。

需要同步主分支、且尚未进入冲突状态时，可在本人的任务分支上先提交任务改动，再执行 `git fetch origin`、`git merge origin/main`。如果产生冲突，按上面的步骤处理。参考：[GitHub 命令行冲突处理](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/resolving-a-merge-conflict-using-the-command-line)。

## 多端接力入口

新电脑先克隆仓库。AI 默认按 AGENTS.md 读取短摘要，再读本次相关的模块；成员需要了解整体项目时阅读 README 和模块索引，不要求每次通读。已有克隆先检查未提交改动、当前分支与上游，再安全获取更新；不要覆盖或重置尚未交接的工作。

工作结束时，将任务相关文件提交并推送，在 Issue 或交接记录中附上分支、提交/PR 链接、已验证内容和下一步。另一端只有成功获取对应提交，才拿到这些文件；本地未提交内容与聊天消息不会自动转成远端成果。

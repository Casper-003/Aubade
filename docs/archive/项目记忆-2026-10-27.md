## 3. 技术路线与架构

### 3.1 技术方向

按照本次请求，采用 C# + .NET + WinUI 3，使用 XAML 构建 Windows 桌面 UI，以 MVVM 组织界面状态与交互逻辑。WinUI 3 属于 Windows App SDK 技术体系。

C# 与 C++ 有相似的控制流语法，但内存管理、类型系统和库的使用方式有明显区别，不能视作简单替换。现阶段以 C# 完成主体。若后续验证确实需要原生音频能力，再通过清晰的接口接入相应库，不因“涉及音视频”就预设整个项目必须改用 C++。

本文不指定未经核验的 .NET、Windows App SDK 或第三方包版本。建立项目后，应记录实际可构建的版本；有需要时用 global.json 固定 .NET SDK，并统一包版本和开发工作负载。

### 3.2 职责划分（实施建议）

| 部分 | 负责什么 | Vesper 示例 |
| --- | --- | --- |
| View | 页面布局、样式、动画及确实依赖界面的行为 | 曲库页、播放页、队列面板、设置页 |
| ViewModel | 可绑定的状态、命令、页面协调 | 搜索词、当前歌曲、播放状态、添加到队列命令 |
| Model / Core | 业务数据与规则 | Song、QueueItem、队列顺序、曲目元数据 |
| Services / Infrastructure | 文件、存储、播放、设备等外部能力 | 曲库扫描、设置保存、媒体播放适配 |

可考虑 CommunityToolkit.Mvvm 简化属性通知和命令；这属于实现选项，是否已经引入应查项目文件。MVVM 的目的在于减少耦合，纯界面行为可以放在适当的 code-behind 中，不必为了形式而强行拆分。

初期可以只保留一个应用项目，按 Views、ViewModels、Models、Services、Styles 等目录组织。需要独立测试或复用时再拆 Core 和 Infrastructure，避免一开始搭建过重框架。

建议的服务边界：

- 曲库服务：扫描用户选择的本地目录，建立和查询歌曲索引。
- 队列服务：添加、删除、调整顺序和选择下一首。
- 播放服务：装载、播放、暂停、切歌、进度、音量和播放状态通知。
- 歌词服务：组织本地歌词、候选在线匹配、统一歌词时间轴和偏移设置；歌词获取、格式处理和界面渲染分别封装，详见 3.4。
- 设置服务：保存可移植的应用设置，区分本机路径、设备标识等本机信息。
- 音频引擎与设备服务：围绕 3.3 已确认的三种音频模式设计设备选择、返听与切换边界，先验证延迟与跨设备稳定性；具体实现阶段仍待安排。

播放器、数据库和音频库的具体选择仍待验证。用接口或适配层隔离这些能力，避免 ViewModel 绑定某个播放器实现；异步扫描与媒体操作应避免阻塞界面，并考虑取消、错误提示和资源释放。

参考：[Microsoft：MVVM 与数据绑定](https://learn.microsoft.com/en-us/windows/apps/develop/data-binding/data-binding-and-mvvm)、[Windows App SDK](https://github.com/microsoft/WindowsAppSDK)。

### 3.3 麦克风返听的三种音频模式（2026-10-26 确认设计，尚未实现）

用户希望保留以下三种 WASAPI 路径，并能在设置中自由切换。以下默认值、切换流程和工程安排为实施建议，不表示已完成验证或编码。

| 用户可选模式 | 技术方向 | 预期行为与边界 |
| --- | --- | --- |
| 共享低延迟（建议默认） | WASAPI IAudioClient3；查询设备支持的引擎周期，再初始化事件驱动的共享流 | 允许其他应用共用设备；优先选择经过验证的低延迟稳定配置，不固定假设所有设备支持 96/128 帧 |
| 独占模式 | WASAPI 独占、事件驱动；查询所选设备支持的格式与周期 | 尝试获得更低延迟；独占所打开的端点，其他应用不能同时使用同一端点；Vesper 伴奏和返听需汇入自己的输出链路 |
| 兼容共享 | 标准 WASAPI 共享模式，使用较保守的缓冲配置 | 用于不支持低延迟接口或小缓冲不稳定的设备；返听延迟可能较大。此模式不要求额外实现 DirectSound 或 MME |

产品与切换建议：

- 设置中保留三个明确的模式选项，同时显示设备是否支持、用户偏好和当前实际生效的模式。设备不支持的模式说明原因，不把失败显示为已启用。
- 切换通常需要淡出、停止并重建音频流，再淡入，可能短暂中断声音；保留队列和播放位置。切换失败时尝试恢复先前可用配置，并清楚提示结果，不承诺无缝切换。
- 共享低延迟初始化失败或运行不稳定时，可调整到更大的合法周期；仍不可用时提供兼容共享回退。不自动转入独占模式；若发生回退，显示原因并保留用户原偏好。
- 按本机输入/输出设备组合保存经过验证的设置；更换设备、采样率或驱动后重新探测。
- 录音期间建议暂缓切换或明确处理录音片段和时间轴，避免静默破坏录音连续性。

技术事实与实现边界：

- **延迟数字不是设备通用保证**：10–18ms 可作为部分目标设备的实测目标，不能仅凭 WASAPI 模式、缓冲帧数或驱动报告就承诺总往返延迟，也不能将主观无延迟感写成通用标准。区分引擎周期、软件估算延迟与实际测得的整条音频链路延迟；需测量并记录设备、驱动、格式和效果设置。
- **双设备时钟同步**：USB 麦克风和板载输出可能使用独立时钟。即使标称采样率一致，也需为漂移设计缓冲和速率匹配；可采用预分配环形缓冲、时间戳/水位监测与平滑自适应重采样。具体控制策略、插值质量和调整范围经长时间测试确定，不直接照搬固定比例。
- **RAW 的正确用法**：通过 IAudioClient2::SetClientProperties 设置 AudioClientProperties.Options = AUDCLNT_STREAMOPTIONS_RAW，并在初始化前探测/处理不支持情况；不存在所引述的 AUDCLNT_STREAMFLAGS_RAW 用法。RAW 仍允许端点特有、始终开启的 APO、驱动或硬件处理，不能宣称强制绕过所有音效。音频类别按实际用途选择，不用通信类别充当关闭特效的手段。
- **实时线程只做有界的音频工作**：文件读取与媒体解码放到后台预取；实时输出路径消费已解码数据，执行必要的重采样、DSP 和混音。避免在实时回调中读文件、解码媒体、分配内存、等待锁或调用 UI。伴奏与人声共用输出时间基准，不要求采集、解码和输出都在同一线程。
- **录音与音画对齐单独验证**：使用采集时间戳、输出时钟和处理延迟建立共同时间轴，必要时提供实测校准；驱动报告的输入/输出延迟不能保证完整覆盖 USB、设备 DSP 和实际播放链路。视频和歌词显示也需跟随音频时间轴。
- 三种模式共用曲库、播放协调、DSP、设备管理和状态接口；C# / WinUI 3 / MVVM 主路线保持。原生音频模块是否需要，以及 miniaudio、JUCE、PortAudio 或其他封装的选择，仍待能力、兼容性与许可验证，不因保留三种模式就同时引入三套库。

建议先验证普通 USB 麦克风 + 板载有线输出组合：测试三种模式的可用性、往返延迟、长时间漂移、爆音/欠载、模式切换及设备拔插恢复，再决定默认缓冲策略和支持范围。

参考：[Microsoft：低延迟音频](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)、[IAudioClient3::InitializeSharedAudioStream](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)、[AUDCLNT_STREAMOPTIONS / RAW 边界](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/ne-audioclient-audclnt_streamoptions)。

### 3.4 曲库来源与歌词方向（2026-10-26 新增，尚未实现）

**已确认与候选范围：**

- 当前以本地曲库为确定路线，支持用户提供的歌曲与 MV；主界面中央仍以曲目推荐为主要内容。首版推荐可以先基于本地曲库、最近播放、收藏等简单规则实现，这是实施建议，不代表已确定推荐算法。
- 用户提出可探索 B 站视频搜索 MV 的方案。将其保留为候选扩展，不视为已验证、已获得所需接口权限或已纳入首版。搜索/跳转官方页面、嵌入网页播放器、取得媒体交由原生引擎播放是不同能力，应分别核验；当前未核实官方接口能覆盖完整的搜索与原生播放需求。
- B 站等网页播放器能否统一播放控制、可靠预加载、同步歌词以及接入 3.3 的独占音频输出，需要单独验证。不能从“网页能播放”推导出与本地 MV 具有相同的混音、录音或无缝切换能力。通过媒体来源与播放器适配层隔离这些差异。
- 用户希望参考 Lyricify 的歌词体验，尤其是本地歌曲没有附带歌词时，仍可搜索并展示逐字歌词。具体代码复用方案仍待集成验证。

**已核对的 Lyricify 范围与实施建议：**

- WXRIW/Lyricify-Lyrics-Helper 是 .NET 歌词工具库，采用 Apache License 2.0；项目文档列出歌曲匹配、在线歌词获取、逐行/逐字歌词处理，以及 LRC、QRC、KRC、YRC、TTML 等格式支持，可优先评估与 C# 主体集成。
- 复用该库时按其许可证保留适用的许可、版权及 NOTICE 信息，修改代码时按要求记录修改。不要将 Lyricify 应用的全部实现、视觉素材或在线词库都视为随该工具库一起开放授权；数据来源的访问条件与可用性单独核验。
- “本地没有歌词也能找到”可以通过曲名、歌手、专辑和时长匹配在线来源实现；不等于任意歌曲都必有逐字歌词，也不等于自动从音频生成精确逐字时间戳。在线来源可能受凭据、地区与服务可用性影响。
- 建议顺序：已有本地歌词 → 在线匹配并确认版本 → 逐字歌词展示；找不到逐字数据时回退逐行或普通文本，并保留手动选择歌词与调整偏移的入口。缓存按来源允许的方式保存在本机。
- 同一首歌的 MV、专辑版、现场版、伴奏版可能具有不同前奏、剪辑或速度，不能只按曲名套用时间轴。匹配版本和时长，必要时校准；歌词时间跟随实际播放时钟。
- 将歌词数据处理与 WinUI 歌词渲染分开。MV 自带烧录歌词与额外叠加歌词是不同显示方式，建议提供选择，避免重复覆盖；纯音频曲目可考虑使用歌词舞台与封面背景。

参考：[Lyricify 主仓库的开源说明](https://github.com/WXRIW/Lyricify-App#lyricify-开源)、[Lyrics Helper 功能与格式](https://github.com/WXRIW/Lyricify-Lyrics-Helper)、[Lyrics Helper 许可证](https://github.com/WXRIW/Lyricify-Lyrics-Helper/blob/master/LICENSE)、[在线接口与凭据说明](https://github.com/WXRIW/Lyricify-Lyrics-Helper/blob/master/docs/providers.md)、[B 站开放平台文档入口](https://open.bilibili.com/doc)。

### 3.5 手机点歌的当前范围（本会话已选定方向，尚未实现）

用户已选择先采用局域网网页点歌方案，手机无需安装专用 App；电脑保存曲库、播放状态与队列，手机用于选歌和控制。公网中转作为后续候选，不作为当前首版前提。

手机与电脑已有可互访的局域网时，扫码打开点歌网页。电脑热点可作为接入方式候选；连接热点与打开网页是两个动作，双二维码是待验证的引导建议，不承诺所有手机扫码后能自动连网再打开网页。昵称、头像、代点、删除与排序权限仍按 5.5 的讨论稿逐项确认。

## 4. 功能优先级（建议，尚非已核验的原始排期）

先实现一条能在家里实际唱歌的流程：**找到本地歌曲 → 加入队列 → 播放 → 切下一首**。

| 优先级 | 建议内容 | 需要注意 |
| --- | --- | --- |
| P0：技术验证 | 用一小组有权使用的媒体验证播放、格式与音轨；确认麦克风和音箱的实际连接方式 | 先明确硬件是否已承担混音与效果处理 |
| P1：最小可用版本 | 本地目录导入或扫描、基础歌曲列表与搜索、点歌队列、播放/暂停/切歌、基本音量与播放状态 | 做完整流程，并保留加载、空列表和错误状态 |
| P1：随核心功能建设 | 统一视觉规范、关键页面、组件和操作反馈 | UI 质量贯穿开发，先把最常用路径做好 |
| 已确认方向，具体排期待定 | 单屏卡拉 OK 视频全屏、双屏一屏视频一屏主界面、可收起队列和悬浮按钮展开过渡；歌词体验参考 Lyricify | 设计细节见 3.4、5.1–5.3，尚未实现或实机验证 |
| P2：体验扩展 | 曲库管理、收藏、快捷键及其他体验完善 | 具体优先级需由实际使用场景决定 |
| 实现阶段与范围待评估 | 麦克风返听的三种 WASAPI 模式方向已确认（见 3.3）；混音、混响、录音、变调、评分、联网曲库、手机点歌等仍需安排具体范围与阶段 | 需求确认不代表功能已实现，也不自动代表全部进入首版 |

媒体相关功能必须说明前提：

- “原唱/伴唱切换”依赖素材确实提供独立音轨、约定的声道布局或独立文件。普通立体声歌曲不一定能直接切换。
- AI 人声分离与音轨切换是不同能力；前者是单独的技术、性能与效果评估项。
- 视频内已经烧录的歌词可以随画面播放；LRC、逐字歌词或独立歌词渲染需要另外确定格式与同步方式。
- 播放伴奏与实时处理麦克风声音是两条工作链路。若使用声卡或硬件混音器处理人声，软件首版未必需要承担实时混音。
- 低延迟监听、回声、啸叫、音画同步和设备兼容需要实机验证，不能只靠 UI 原型判断。

## 5. Figma 与 UI 设计

原对话中，用户询问过：是否能在 Figma 中把全部界面设计好，再补充控件功能与交互；也在思考 UI 是否应该留到主要功能完成后。

建议采用迭代方式：先梳理核心流程和关键页面，再做可点击原型，同时用一个小型 WinUI 界面与播放验证检查可行性。可以预先规划全部页面，但没有必要在第一次编码之前冻结所有细节。

Figma Design 可用于设计页面、组件、布局和视觉规范，并通过原型连接描述点击、页面跳转、覆盖层与动画等交互。它可以帮助验证“用户如何操作”；本项目仍需要在 C#/XAML 和服务层实现文件读取、媒体解码、音频路由、持久化等真实行为。不要把可点击原型当作完成的 Windows 应用，也不要预设设计稿能无损自动转换为生产可用的 WinUI 3 工程。

建议优先设计：

1. 曲库与搜索：怎样找到歌曲、怎样加入队列。
2. 队列与正在播放：当前曲目、下一首、移除或调整顺序。
3. 播放画面：视频或歌词区域、常用控制、全屏。
4. 设置与状态：曲库目录、设备选择，以及空列表、加载和失败提示。

建立最小设计规范：颜色、字号、间距、圆角、按钮与列表状态、焦点和键盘反馈。设计时同时考虑 Windows 窗口缩放、显示缩放、可读性和家庭使用距离。最终规范应在 WinUI 实机中检查。

在仓库的 docs/design.md 或 README 中记录 Figma 链接、当前采用的页面或版本、关键交互和已确认的设计决定。必要时保存适量预览图；不要认为 Git 会自动同步 Figma 的云端设计内容。

### 5.2 卡拉 OK 的单屏与双屏行为（用户已确认）

| 场景 | 进入卡拉 OK 模式后的表现 |
| --- | --- |
| 单屏幕 | 视频在该屏幕全屏播放 |
| 双屏幕 | 一块屏幕全屏播放视频，另一块屏幕保留主界面用于选歌和管理队列 |

用户已采纳：允许指定视频输出屏幕并记住选择；双屏动画按 5.3 在目标视频屏呈现，控制屏保留主界面。

实施建议：

- 双屏使用 Windows 扩展桌面模式；复制屏幕模式不能呈现两套独立内容。允许用户指定视频输出屏幕并记住选择，不固定假设“第二块屏幕”永远是电视。
- C# / WinUI 3 主体使用独立的视频呈现窗口与主界面窗口，由同一播放会话、队列和时间轴协调。切换显示方式尽量保留播放器状态，不重新开始歌曲；按播放器实际能力验证画面承载方式。
- 显示器选择与声音输出设备分别设置；连接电视不必自动切走原有返听或音箱输出。
- 设计 Esc/返回按钮退出全屏的行为，恢复主界面及原布局；显示器断开时迁回可用屏幕，避免窗口遗留在屏幕外。这些是建议的异常恢复规则，尚未实现。

参考：[Microsoft：WinUI 与 Windows App SDK 窗口模型](https://learn.microsoft.com/en-us/windows/apps/develop/ui/windowing-overview)、[窗口与全屏管理](https://learn.microsoft.com/en-us/windows/apps/develop/ui/manage-app-windows)。

### 5.3 悬浮播放入口与展开过渡（用户已确认方向）

用户原希望中央区域右下角的较大播放按钮带有 Google 风格；点击后，通过动画将按钮扩大到整个屏幕，再无缝衔接卡拉 OK MV。可参考 Material 悬浮操作按钮（FAB）与容器形变的设计思路。2026-10-27 用户重新评估是否改为顶部固定入口，位置与相应动画形态仍待讨论；颜色、形状、阴影和时长也未定稿。

建议的过渡流程：

1. 确认目标曲目和视频输出屏幕，准备播放资源及可显示的首帧。
2. 按钮提供按下反馈，以圆角、尺寸和遮罩变化扩展过渡层。
3. 在画面准备好后，将过渡层与视频画面平滑交接，同时保持音频和播放时间连续。
4. 若媒体加载较慢或失败，显示明确状态并允许取消；动画结束不等于媒体已成功开始播放。

用户已采纳：单屏在同一屏幕完成按钮到全屏的形变；双屏时控制屏按钮提供反馈，在目标视频屏幕完成展开/显现，控制屏继续保留主界面。跨屏动画的具体视觉形式与节奏仍需原型验证。

实现时将过渡动画与媒体生命周期分开，预加载/首帧就绪后再交接，避免每次动画都销毁和新建播放器。根据实际视频渲染承载方式验证过渡层覆盖与跨窗口表现；遵循系统减少动画的设置，提供简化过渡。

**本轮评审建议（待用户回应）：**

- 列表用于辨认和选歌，建议优先显示歌手；作词、作曲及专辑介绍放在详情页。详情页联网补充不应妨碍本地浏览，缺失资料有简洁状态。

- 右侧队列常态建议只留细小但可发现的拉手/数量提示，展开后确保内容清楚可读；提供点击和键盘入口，光标移入面板后保持展开，支持关闭。队列控件内不扩大为选歌界面。

- 右键插播可保留，同时提供可见的“更多”入口供触摸与手机使用；文案可使用“排到下一首”，与立即打断当前歌曲区分。当前正在唱的歌曲不参与普通待播队列重排。
- 预设排序需明确是持续规则还是一次性整理。建议拖动后清楚切换到手动排序，避免拖完自动跳回；一人一首按演唱者轮换，并定义新人加入、插播与新点歌曲的位置。
- 代点需要区分操作人和演唱者。建议由演唱者决定轮唱归属，并在项目上显示“某某演唱，某某代点”；演唱者可移除代点项，操作人能否撤回仍待确认。建议考虑主人可管理全队列的例外；所有人可排序时可提供轻量操作提示及撤销。
- 昵称与头像编辑尽量轻量，默认头像可直接使用，用户自行选择更换；代点提醒以不遮挡演唱的通知呈现。重复点歌提示应说明当前队列中已有的版本、演唱者和位置，允许明确选择再点一次。
- 队列为空与结束房间分别定义：Logo 可作为等待背景，同时给出继续点歌入口；是否保持参与者和房间，以及空队列后新点歌曲是否自动开唱，仍需确定。“退出本场”的影响与权限要写清楚。

参考交互原则：[W3C：悬浮内容可关闭、可移入且保持可见](https://www.w3.org/WAI/WCAG21/Understanding/content-on-hover-or-focus)、[W3C：自动播放声音的可控性](https://www.w3.org/WAI/WCAG21/Understanding/audio-control.html)。这些网页交互原则用于辅助桌面体验评审，不将其表述为已完成可访问性验证。

## 6. 媒体与版权边界（建议作为项目约束）

原对话中更早的媒体来源和授权讨论未能读取，因此以下是建议采用的实施边界，不能写成已核实的历史承诺：

- 首版优先处理用户自行提供、并确认具有相应用途权限的本地媒体。
- 不默认附带商业歌曲、伴奏、MV、歌词库、封面或完整曲库；演示素材使用自制或授权范围明确的资源。
- 不将抓取付费曲库、绕过登录或 DRM、破解下载限制作为既定功能。
- 本地播放、打包分发、上传分享、公开演唱和商业使用需要分别核对素材授权；“个人学习”或“仓库私有”不能直接作为所有用途的授权依据。
- 若以后接入在线服务，先确认其接口、使用条款及所需授权，再安排开发。
- 播放器、音频库、字体、图标等第三方依赖的许可证与再分发要求也要记录；不要默认依赖可用就能任意随安装包发布。

代码仓库与个人曲库分开管理。大体积歌曲、录音、封面缓存和个人数据库通常不进入 Git。确需版本管理的少量授权测试素材，应单独整理来源与许可；Git LFS 只处理大文件存储问题，不解决授权问题。

## 7. 两台电脑交替开发：基本约定

2026-10-27 新增团队背景：用户已建立仓库 [Casper-003/Vesper](https://github.com/Casper-003/Vesper)，并说明已有一位协作者；默认分支为 main。本次资料入库以保留已有 LICENSE 和现有本地文档为前提，为团队建立 README、模块索引、记忆与协作指南。每次接续以实际 Git 状态和远端提交为准，不能仅凭本文判断某台电脑是否已同步。

两人分工、任务粒度与进度交接的建议整理在 [docs/协作指南.md](../协作指南.md)，其中具体流程仍属建议稿，未自动作为全员已同意的规则。本节的两台电脑说明与两位协作者是不同维度：每个人仍分别管理自己的克隆与未提交工作。新成员先读 README 与模块索引，再结合本文件核对当前设计状态。

GitHub 托管远程仓库。**保存文件不会上传，commit 不会上传，push 也不会让另一台电脑自动更新。** 另一台电脑仍需主动获取并整合远端提交。通常也不会同步未跟踪文件、被忽略文件、本地 stash、IDE 会话或应用运行数据。

推荐每台电脑各自 clone 同一个仓库，不把同一个工作目录交给 OneDrive 等网盘同时同步。两台电脑的本地路径可以不同。

日常顺序是：

**开工：检查状态 → 确认分支 → 拉取更新 → 修改。**
**收工：检查改动 → 验证 → 小步提交 → 推送成功 → 再换电脑。**

关键约定：

- 一个功能使用一条短期分支，例如 feat/local-library、feat/player-ui 或 fix/queue-order；main 保存已验证的可用状态。
- 分支按任务划分，不必长期分成“电脑 A 分支”和“电脑 B 分支”。
- 在两台电脑上接着做同一个任务时，接续同一条远端功能分支；首次接续与日后接续的命令不同，见下一节。
- 同一时间只让一台电脑修改同一任务。尤其避免两边同时留下没有交接的未提交或未推送改动。
- 确需同时做不同任务时，使用不同功能分支，尽量减少修改同一文件，完成后再整合；这只能降低冲突概率，不能保证无冲突。
- 小提交以“一个能说清的改动”为单位，例如一个播放控制、一个页面状态或一个问题修复；无需每敲几行就提交。
- 换电脑前，即使功能未完成，也可以在功能分支提交明确标为 wip 的阶段快照并推送，再记录哪些部分尚不可用。
- 没网络时 commit 只能保存在当前电脑。未成功 push 前不要把交接当作完成；若两边离线并行修改，恢复联网后需要主动合并。

## 8. 可以照着使用的 Git 命令

以下为 Windows PowerShell 中的示例，**不是已在你的仓库执行的操作**。将 OWNER 换为实际 GitHub 用户名或组织名，将 D:\Dev\Vesper 换为自己的目录。示例假定远端叫 origin、默认分支叫 main，且仓库已经有首个提交；实际命名不同就相应替换。

每个命令成功后再继续。遇到冲突、登录失败或推送被拒绝时，先处理原因。

### 8.1 首次准备：两台电脑分别做一次

先在 GitHub 准备同一个仓库，再分别克隆。已有本地仓库的电脑不用再次 clone，也不要重新 init 来覆盖现有关系；先检查 git remote -v。

    git clone "https://github.com/OWNER/Vesper.git" "D:\Dev\Vesper"
    Set-Location "D:\Dev\Vesper"
    git remote -v
    git branch --show-current
    git status
    git config pull.ff only

最后一行只设置当前克隆的默认拉取策略，因此两台电脑各自设置。它让出现分叉时先停下来，不会自动替你决定如何合并。

首次提交前，两台电脑分别设置作者身份，替换示例内容；邮箱可以使用自己实际的 GitHub noreply 地址：

    git config user.name "你的提交署名"
    git config user.email "你的实际提交邮箱"

作者身份不是登录凭据。两台电脑都需要配置自己的 GitHub 访问方式；凭据或访问令牌不写进仓库。

参考：[git clone](https://git-scm.com/docs/git-clone)、[git pull](https://git-scm.com/docs/git-pull)。

### 8.2 电脑 A：从最新 main 开始一个新任务

先检查 git status，确认没有需要保留的未提交改动，再执行后面的切换与拉取：

    Set-Location "D:\Dev\Vesper"
    git status
    git switch main
    git pull --ff-only
    git switch -c feat/local-library

feat/local-library 只是任务分支示例；新任务选一个合适的新名称，已有分支不要重复创建。

修改后，先检查差异，并按现有解决方案的方式构建或运行相关功能。确认 .gitignore 正确、没有媒体与敏感配置混入，再暂存和提交：

    git diff
    git status --short
    git add .
    git diff --cached
    git commit -m "feat: add local song import"
    git push -u origin feat/local-library

git add . 会暂存当前目录下所有符合条件的改动，包含新文件和删除；也可以改为只 add 本次任务涉及的具体路径。提交前务必看暂存区差异。

第一次 push 使用 -u 建立上游关系；以后在这条分支可以直接 git push。只有看到成功输出，才算提交到远端。

### 8.3 电脑 B：第一次接续这条功能分支

先确认工作区干净，再取得远端分支并建立本地跟踪分支：

    Set-Location "D:\Dev\Vesper"
    git status
    git fetch origin
    git switch --track origin/feat/local-library
    git pull --ff-only

如果电脑 B 已经有同名本地分支，使用下一节的 git switch feat/local-library；不再执行 --track 创建一次。

参考：[git switch](https://git-scm.com/docs/git-switch)。

### 8.4 任一电脑：后续每天继续已有任务

确认 git status 干净，再接着执行：

    Set-Location "D:\Dev\Vesper"
    git status
    git switch feat/local-library
    git pull --ff-only

完成一个小改动后提交；收工前推送：

    git diff
    git status --short
    git add .
    git diff --cached
    git commit -m "fix: handle missing media files"
    git push
    git fetch origin
    git status -sb

最后检查：没有本次任务遗留的未提交改动，当前分支相对上游没有 ahead 或 behind。fetch 或 push 失败时，这个检查不能证明同步完成。

不要为了执行模板而创建没有改动的提交；commit 提示没有内容时，检查是否还有尚未 push 的旧提交。

### 8.5 还没完成，但必须换电脑

在功能分支检查并保存阶段性改动，说明尚未完成的部分：

    git diff
    git status --short
    git add .
    git diff --cached
    git commit -m "wip: save song import progress for handoff"
    git push

WIP 提交用于交接，不意味着功能已验证。另一台电脑按前面的接续流程拉取；不要把明显不可用的阶段快照直接合入 main。

### 8.6 功能完成后合入 main

建议检查差异与验证结果后，通过 GitHub PR 将功能分支合入 main。个人项目也可以开 PR 自查，描述具体行为变化、验证情况和已知问题。

如果没有分支保护、采用本地合并流程，先确认工作区干净，且功能分支已完成、已推送，再执行：

    git switch main
    git pull --ff-only
    git merge --no-ff feat/local-library
    git push origin main

合并有冲突就先处理，不能直接继续 push。如果仓库要求 PR，就通过 PR 合并，不绕过规则。两种合并方式选一种即可。

PR 或本地合并成功后，另一台电脑更新 main：

    git switch main
    git pull --ff-only

建议每个新任务从更新后的 main 创建新分支。使用 squash 合并的旧功能分支尤其不要继续承载新任务。

参考：[git merge](https://git-scm.com/docs/git-merge)、[git push](https://git-scm.com/docs/git-push)。

## 9. 遇到同步问题时怎么处理

### 9.1 开工时发现本机还有未提交改动

先看 git status 和 git diff。需要交接的改动，优先在正确的功能分支提交并推送；仅需在本机临时收起的改动，可以暂存：

    git stash push -u -m "local work before sync"
    git pull --ff-only
    git stash apply

上述操作假定当前就在需要同步的分支。-u 包含未跟踪文件，但不包含被忽略文件。apply 后检查改动和冲突；确认恢复完整后才按需删除相应 stash。

**stash 默认只在当前电脑中，不会随普通 push 上传；它不是跨电脑交接办法。** 工作区干净也不等于电脑里没有尚未交接的 stash。

参考：[git stash](https://git-scm.com/docs/git-stash)。

### 9.2 两台电脑都已经在同一分支各自提交，push 被拒绝

如果提示 non-fast-forward，通常说明远端还有本机未整合的提交。先确保本地改动已经提交、工作区干净，然后保留一个备份分支，再获取和合并：

    git branch backup/pc-b-before-sync
    git fetch origin
    git merge origin/feat/local-library

备份分支名称需要唯一；它只保留已提交的状态。示例假定当前就在 feat/local-library；实际分支不同就替换名称。

没有冲突时，检查并验证合并结果，再 git push。有冲突时按下一节处理。若推送因权限、分支保护或网络失败，应处理对应原因，不能一概当成代码冲突。

对于仅存在本机、从未发布的提交，也可以在了解影响后使用 rebase 整理；日常入门流程先用 merge，减少重写历史带来的交接问题。

### 9.3 出现文件冲突

1. 执行 git status 查看冲突文件。
2. 在编辑器中理解两侧改动，整理出正确的合并结果，删除冲突标记；不要机械选择“全部保留本地”或“全部保留远端”。
3. 将解决后的具体文件暂存，完成合并，验证并推送。下面的文件名是示例，替换为实际冲突路径：

    git add -- "src/Vesper.App/ViewModels/LibraryViewModel.cs"
    git commit -m "merge: resolve local library conflicts"
    git push

如果刚开始合并就发现不适合继续，在本节规定的“合并前工作区干净”条件下，可以取消本次合并：

    git merge --abort

若实际进行的是 rebase，解决后使用 git rebase --continue，取消则用 git rebase --abort，不要与 merge 流程混用。

不要把 git push --force、删除整个工作目录或 git reset --hard 当成常规同步方式。先保留双方工作，再决定怎样整合；文本能自动合并，也仍可能存在行为上的冲突，需要构建或运行检查。

参考：[GitHub：在命令行解决合并冲突](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/resolving-a-merge-conflict-using-the-command-line)。

## 10. 哪些文件同步，哪些留在本机

建议将源代码、项目与解决方案文件、共享配置、必要且可分发的资源、文档和 .gitignore 提交到仓库。

两台电脑各自安装匹配的开发工具、Windows SDK 和相关工作负载；根据仓库版本恢复 NuGet 依赖、构建运行。源码同步成功不代表开发环境自动相同。把实际依赖和构建步骤写入 README；不要同步 bin、obj 来代替环境配置。

以下为 .gitignore 起点，需要结合实际项目调整：

    # IDE 与构建结果
    .vs/
    [Bb]in/
    [Oo]bj/
    *.user
    *.suo
    TestResults/
    AppPackages/

    # 本机配置、凭据与个人数据
    .env
    .env.*
    !.env.example
    appsettings.Local.json
    *.pfx
    *.p12
    local-data/
    media-library/
    recordings/
    logs/

目录名需要与实际数据存放约定一致。不要笼统忽略所有 Assets、JSON、图片或媒体扩展名，否则可能误排除应用资源和合法测试素材。

- 曲库路径、声卡设备标识、最近播放记录、缓存数据库等放在本机数据目录；可共享的设置提供不含私密值的样例。
- 项目和解决方案、包清单、共享构建配置通常需要提交；已有锁文件策略就按项目约定执行。
- .gitignore 需要提交到仓库，两台电脑才能共享这些规则。
- .gitignore 不会自动停止跟踪已经提交的文件。若只需从跟踪中移除而保留本机文件，应针对核对过的具体路径处理；曾上传的凭据还需要撤销或轮换，不能只追加忽略规则。

可在仓库初始化时统一文本换行，例如将以下内容保存为 .gitattributes：

    * text=auto
    *.cs text eol=lf
    *.xaml text eol=lf
    *.md text eol=lf
    *.json text eol=lf
    *.ps1 text eol=crlf

Markdown、C#、XAML 等文本建议统一使用 UTF-8。已有仓库若要重新规范换行，先检查影响，单独提交纯格式变化，避免与功能修改混在一起。

参考：[GitHub：忽略文件](https://docs.github.com/en/get-started/git-basics/ignoring-files)、[Git：文本属性与换行](https://git-scm.com/docs/gitattributes)。

## 11. README、CHANGELOG、项目记忆与交接记录

| 记录位置 | 主要用途 | 更新时机 |
| --- | --- | --- |
| README.md | 项目是什么、环境要求、怎样构建运行、主要入口与设计链接 | 使用或构建方法变化时 |
| CHANGELOG.md | 按版本或阶段记录对使用者有意义的新增、修复和行为变化 | 有值得记录的变化或发布时 |
| Vesper_项目记忆.md | 长期目标、已确定的技术选择、设计偏好、约束、重要决定的理由和待确认项 | 项目方向或关键决定变化时 |
| Git commit | 每个可追溯的小改动及其原因；实际代码差异由 Git 保存 | 每个合适的小改动完成时 |
| GitHub Issues（可选） | 需求、问题、验收标准、待办和探索结论 | 出现任务或问题时 |
| GitHub PRs（可选） | 一批改动的审查、验证结果与合并记录 | 准备整合功能时 |
| docs/交接.md（可选） | 当前分支、做到哪里、已知问题、下一步和验证办法 | 换电脑或换开发会话时 |

无需把每个 commit 的内容重复追加到记忆文件。记忆文件保持“当前共识”，Git 保存细节历史，CHANGELOG 保存有意义的版本变化。小改动不必更新全部文档；但影响架构、目标、约束或接续判断的变化应及时记录。

分支用于组织代码，Issue 用于说明要做什么，PR 用于说明做了什么和是否适合合并。Issue 或 PR 不会代替两台电脑的 pull/push，也不会上传未提交改动。

可采用下面的交接模板：

    日期：
    工作分支：
    最近已推送提交：
    本次完成：
    已验证：
    未完成 / 已知问题：
    下一步：
    本机环境或媒体前提：

交接记录与相关代码一起提交并推送，不只留在某台电脑或某个聊天窗口。两台电脑若都追加同一文件末尾，也可能冲突；保持简短、按日期整理即可，不必复制聊天全文。

## 12. 后续接续时的核对清单

先阅读实际仓库中的现有说明和本文件，再确认：

1. 当前分支、未提交改动和远端状态；先安全同步，再开始修改。
2. 仓库真实结构、可构建的 SDK/包版本，以及当前已完成的功能。
3. 第一条要打通的家庭 KTV 流程和这次任务的验收标准。
4. 实际媒体格式、原唱/伴唱组织方式、歌词方式与设备链路。
5. 是否已有 Figma 文件；落实 5.1–5.3 已确认的主界面、单/双屏与动画方向，并核对仍待确认的视觉和交互细节。
6. 播放器、音频库、存储方案和发行方式中哪些仍只是候选。
7. 本次变更是否需要更新 README、项目记忆或交接记录。

优先保留明确需求：Windows 家庭 KTV、C# / WinUI 3 / .NET / MVVM、重视 UI 品质、支持两台电脑交替本地开发。不要把本文标注的建议当成已实现功能，也不要为了补齐上下文而虚构原对话内容。
